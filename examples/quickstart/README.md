# quickstart: 6-task open-ended end-to-end demo

This is not a "should just work" scaffolding walkthrough — the `produced/` and `report/` directories here are **actual artifacts left behind after running an agent through the verifier-author pipeline once**, not hand-written examples. The goal is to let you see (and rerun yourself) exactly how "writing a verifier for an open-ended task" happens, without needing the full 150-task raw dataset.

## Directory Structure

```
examples/quickstart/
├── skill/              a snapshot of the delivered skill (see "Which version of the skill is this" below)
├── bench/              two-layer "questions + answers" structure for the 6 tasks (staged artifact, see benchmark/README.md)
│   └── tasks/<task_id>/
│       ├── verifier_author_inputs/   questions: task_md + inputs + candidate submissions from 8 models
│       └── gold_verifier/            answers: official grader/labels (used only during grading; author never sees this)
├── produced/<task_id>/ grader.py / rubric.md / verifier_summary.md actually generated by the author
│                        (some tasks also include a judge_harness.py, see below)
├── report/              consistency report produced by evaluate_bench
└── scripts/
    ├── stage_demo.py    re-stage these 6 tasks from raw data (requires origin_data/ locally)
    ├── run_author.sh    rerun author for a single task using your own agent CLI
    └── run_evaluate.sh  run grading, regenerating report/
```

## How These 6 Tasks Were Selected

All follow the same naming convention (`task_<slug>`), all trace upstream to the same PawBench sub-source, **pinchbench** (see `origin_data/SOURCES.md`), and all are **open-ended** tasks — there is no single "correct answer"; the verifier has to induce its own subjective scoring dimensions rather than checking off a handful of deterministic checkpoints:


| task_id                            | Task Type                     | Grading Challenge                |
| ---------------------------------- | ------------------------ | ------------------- |
| `task_blog`                        | Write a 500-word blog post              | Content quality / topical relevance, no single correct text |
| `task_contract_analysis`           | Read a PDF contract and perform legal analysis            | Whether risks are adequately identified is subjective       |
| `task_meeting_advisory_attendees`  | Extract attendee information from a meeting transcript            | Judging roles/nature of statements requires contextual understanding    |
| `task_meeting_gov_data_sources`    | Extract data sources from the NASA UAP hearing transcript  | Completeness of relevance and limitation descriptions       |
| `task_video_transcript_extraction` | Fetch YouTube captions and write a summary        | Summary quality, choice of key points           |
| `task_gh_issue_triage`             | Triage GitHub issues/PRs by priority | Priority ranking is itself a judgment call        |


Selection criterion: across four independent reruns (iter_0→iter_3, same v0 skill, repeated sampling) of the `260701_agenticjudge` experiment, these 6 tasks' agree/8 (number of candidates matching the official grading) **stayed consistently high with low variance** — even though this skill was never actually iterated on, its performance on this batch of open-ended tasks is a genuine, reproducible signal, not a one-off stroke of luck.

## A Real Negative Finding: agentic_judge Never Actually Fired in This Demo

The core selling point of this skill is "for predicates that structurally can't be checked deterministically, actually invoke an LLM agent to judge them" (`invoke_agentic_judge` in `judge_harness.py`). **But in the environment where this report was generated, across all 68 `invoke_agentic_judge` calls corresponding to the 48 observations, `judge_meta.available` was `False` every single time** (the trajectory files written under `report/_judge_trajectories/` are all 0 bytes; the subprocess fails and exits within 1-2 seconds without producing any parseable result — most likely because `cursor-agent` lacks a usable login/session context in this non-interactive shell environment, not a bug in the harness itself).

This was not "fixed" or hidden, because it exposes two real, worth-recording facts:

1. **The failure contract of `invoke_agentic_judge` itself is correct**: when the call fails, it normalizes to `available=False`; the grader does not crash, and `outcome_passed` (which only looks at deterministic must-haves) is completely unaffected — this explains why D1 (0.854) still looks decent.
2. **But D2 (score-level MAE/Spearman) is systematically dragged down**: looking at `grader.py` (e.g. `examples/quickstart/produced/task_blog/grader.py`), when `judge` is unavailable it **fills in a score of 0** for each `agentic_judge_*` dimension and includes it in the score average, instead of excluding that dimension from the average entirely — effectively mistaking "the judge was never reached" for "the judge scored it 0," which drags the score down even though it should only reflect deterministic signals. This is a genuine design gap in the fallback logic that the author agent wrote for itself, not something we found and patched after the fact by modifying the code; `grader.py` is kept as-is to honestly show this.

To verify this yourself: `grep -c '"available": true' report/_judge_trajectories/**/*.jsonl`, or just check the file sizes (all 0 bytes); you can also rerun `run_evaluate.sh` in your own environment with `cursor-agent`/`claude`/`codex` already logged in, and see whether this number changes.

## How to Reproduce

**Just look at the existing artifacts** (no agent CLI/API key needed):

```bash
cat examples/quickstart/report/eval_report.md
```

**Rerun the author step for a specific task** (requires your own logged-in `cursor-agent` / `claude` / `codex`):

```bash
cd examples/quickstart
./scripts/run_author.sh task_blog composer-2.5 cursor-agent
./scripts/run_evaluate.sh
```

**Re-stage these 6 tasks from scratch** (requires a complete `origin_data/` locally; see the root README's "Data & Licensing" section):

```bash
python examples/quickstart/scripts/stage_demo.py
```

## Limitations (No Hiding)

- The `gold_verifier/` (official grading standard/reference answers) for these 6 tasks is also published, in `bench/tasks/<task_id>/gold_verifier/`, so you can verify the numbers in the tables above yourself — but this means **these 6 tasks can no longer be used to test a new version of the verifier-author skill** (it has already "seen the answers," so retesting on these 6 tasks by anyone would not be a clean evaluation). A genuine capability evaluation should use the train/test split of the full 150-task benchmark (data not distributed with this repo; see the root README).
- These 6 tasks were **deliberately selected for "good, stable performance,"** not randomly sampled, and are not a representative slice of the full benchmark — the numbers in this README only show "the upper bound of what this skill can achieve on this type of open-ended task," and cannot be used to infer its overall capability on the remaining 144 tasks (see each experiment directory's `reports/final_report.md` for the honest reporting on that).
- The author's physical isolation (`gold_verifier/` simply does not exist in the sandbox) is the anti-leakage guarantee for this demo; the additional "trajectory forensics" step used in this repo's formal experiments (`benchmark/tools/leak_scan.py`, which scans agent tool-call trajectories) has no corresponding usable trajectory format in this demo. This is a simplification that does not affect the validity of the isolation here, but if you cite this demo in a paper or report, please note it.
- A sample size of 6/8 cannot support statistical significance for any single task; the "breakdown by task" in this README is a qualitative illustration only, not a rigorous capability assessment.
- agentic_judge never actually fired in this run (see the previous section) — what this report actually demonstrates is grading capability based on "deterministic + structured nice-to-have signals"; the agentic_judge design direction itself has not yet been genuinely validated by this demo.
